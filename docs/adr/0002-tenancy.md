# ADR-0002: Tenancy (schema per organization)

Status: accepted, subject to the compatibility spike in "Order of work".

## Context

Each organization's operational data (lockers, parcels, device operations) must be
isolated from every other organization. Users, OTP challenges and tokens are global:
one phone number can belong to several organizations, and sign-in happens before any
organization is known.

## Decision

- **One PostgreSQL schema per organization**, managed with `django-tenants`
  (`Organization` is the tenant model, in the `public` schema).
- **Shared apps (`public`)**: `accounts`, `organizations` (Organization and
  Membership), the token blacklist, admin and auth tables.
  **Tenant apps (per schema)**: lockers, parcels, device operations.
- **Tenant selection happens after authentication, from the database, never from
  client input alone.** The URL carries an organization slug
  (`/api/v1/orgs/<slug>/...`). A base view authenticates the request, loads the
  caller's active `Membership` for that slug, and only then activates the schema.
  No membership gives the same response as an unknown slug (404). The
  hostname-based `TenantMainMiddleware` is not used: a client-controlled `Host`
  header must not choose a schema, and we serve one API domain.
- **The schema is always reset to `public` when the request ends**, including on
  errors, so a reused connection can never carry a previous tenant's `search_path`.
- **Schema names are generated by the server** as `org_` plus 12 random hex
  characters, never from user input. The primary key is not used because it does
  not exist until the first save, which is when the schema is created; random
  names also keep the number of organizations from being guessable.

## Why `django-tenants` and not hand-written schema management

Schema creation, per-schema migrations (`migrate_schemas`), the database router,
`search_path` handling and test helpers are well exercised there. Writing them
ourselves would spend the project's time on plumbing and add leak risks without
adding to what this project demonstrates: isolation guarantees that are tested.
Our own code stays where the risk is specific to this domain: tenant selection
through Membership, reset on exit, and the isolation tests.

Rejected alternatives: row-level `organization_id` filtering (one missed filter leaks
data, and the spec asks for schema isolation); a database per tenant (heavier to
operate, and cross-tenant admin queries get harder).

## Consequences

- **Django must be 5.2 LTS or newer.** The current `django-tenants` releases require
  `django>=5.2`; the project is on 5.1, so the upgrade is a separate first PR.
- **psycopg 3 is supported** by current releases, so the `.sqlstate`-based error
  handling in `accounts` is unaffected. A test must still prove it on our stack.
- **No `Domain` model.** `TENANT_DOMAIN_MODEL` is not set: hostname routing is not
  part of this design, and the library works without it (see
  `tests/test_organizations.py`).
- PostgreSQL stays required (system check `accounts.E006` still holds; the
  `django_tenants` backend reports `postgresql`).
- Migrations of tenant apps run once per schema; CI must run `migrate_schemas` and
  `makemigrations --check`.
- Connection pooling or `CONN_MAX_AGE > 0` makes the reset-on-exit rule load-bearing;
  it is covered by tests.

## Required tests (isolation is the product)

- Data created in one organization is invisible from another, through the API and
  through the ORM.
- A user with no membership, an inactive membership, or a membership in another
  organization cannot reach a tenant URL, and sees the same 404 as an unknown slug.
- The schema is `public` after a successful request, after an exception, and after a
  request that was rejected before activation.
- Concurrent requests for different organizations on real PostgreSQL never see each
  other's rows.
- A forged slug, `Host` header or `X-Forwarded-*` header cannot select a schema.

## Order of work

1. Upgrade Django to 5.2 LTS (own PR, no behaviour change). Done.
2. Spike: add `django-tenants`, confirm `migrate_schemas` and the test helpers work
   with psycopg 3 and our `accounts` constraints. If it fails, revisit this ADR
   before any model work. Done: it works (branch `spike/django-tenants`, kept
   unmerged as a record).
3. `organizations` app: `Organization` (tenant) and `Membership` (user,
   organization, role Admin or Operator, active flag). Done.
4. Provisioning and the tenant-selection base view, with the tests above.
5. Lockers and parcels inside tenant schemas.

## Memberships

- `Membership` lives in `public`: sign-in and tenant selection happen before any
  schema is active, and one user can belong to several organizations.
- One membership per user and organization, and the role is checked by the database
  as well as by validation.
- Organizations are deleted with their memberships, but a user who has memberships
  cannot be deleted; deactivate instead, because tenant records will refer to users.
- `get_active_membership(user, slug)` returns `None` for an unknown slug, somebody
  else's organization and an inactive membership alike, so the HTTP layer can answer
  all three with the same 404.
- Organizations are created only through `create_organization` (a platform
  operator's job). There is no public endpoint for it yet, and opening one is a
  product decision that needs its own limits.

CI runs `migrate_schemas` on a fresh database, because tenant isolation is defined
by the per-schema migrations.

## Tenant selection (implemented)

Endpoints under `/api/v1/orgs/<slug>/` inherit `TenantAPIView`. For each request:

1. Authentication, permissions and throttles run while the schema is `public`.
2. The caller's active membership for the slug is loaded. An unknown slug,
   somebody else's organization and an inactive membership give the same 404.
3. Only then is the organization's schema activated and the handler run.
4. The response is **rendered before the schema is reset.** DRF renders after
   `dispatch` returns, so a lazy queryset left in the response data would be
   evaluated against `public` and return the wrong rows without any error. A test
   pins this.
5. The connection goes back to `public` in a `finally`, including after unhandled
   errors.

The tests (`tests/test_tenant_view.py`, `tests/test_tenant_isolation.py`) cover each
point above, plus forged `Host`, `X-Forwarded-*` and custom headers, and twelve
concurrent threads alternating between two organizations. Until lockers exist they
use rows of `django_content_type`, which is present in `public` and in every
schema, as stand-in tenant data; the same tests must be repeated with real locker
and parcel data when those models arrive.

Work outside a request (Celery tasks, management commands) has no ambient tenant.
It must receive the organization id and activate the schema explicitly with
`tenant_context`, and must never rely on whatever the connection happens to hold.
The view layer assumes synchronous workers.

## Roles and permissions (implemented)

- Two roles: **Admin** and **Operator**. Admins can do everything operators can.
  Admins manage the organization's members; operators do the day-to-day work with
  lockers and parcels (those endpoints come later).
- `IsOrgMember` (any active member) and `IsOrgAdmin` are ordinary DRF permission
  classes. They read `request.membership`, which `TenantViewMixin` sets, and **fail
  closed**: a view that forgot the mixin denies everybody instead of letting
  everybody in. Views choose their level with `permission_classes`.
- Answers: 401 when not signed in, 404 for an unknown slug, somebody else's
  organization or an inactive membership (all identical), and 403 for a member
  whose role is too low. A 403 only ever goes to somebody who already belongs to the
  organization, so it reveals nothing.
- **The role is read from the database on every request**, never from the token or
  a cache. Demoting or deactivating a member therefore applies to their very next
  request even though their token is still valid. The cost is one small query per
  request, which is worth the immediate effect.
- Permission checks run on the `public` schema, before the organization's schema is
  activated, so a denied request never reaches tenant data.
- `Membership` lives in `public`, so schema isolation does not protect it. Views
  that read memberships filter on the caller's own organization explicitly, and a
  test pins that other organizations' members never appear.
- Permissions that depend on the object (for example "an operator may only touch
  parcels at their own locker") are not part of this step and need their own design
  once lockers exist.

Not done yet, deliberately kept for the next step: adding a member, changing a role
and deactivating a member. They need the rule that an organization can never lose its
last admin, and a decision on how to attach a membership to a phone number that has
not signed in yet. The member list is not paginated because organizations have few
members; revisit if that stops being true.
